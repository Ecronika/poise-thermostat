# HA-runtime integration-test harness (CI-only; needs Python >= 3.13.2 AND a
# POSIX host).
#
# WINDOWS CANNOT RUN THIS SUITE ANY MORE (measured 2026-08-15): from exactly
# HA 2025.10 on, `homeassistant/runner.py` imports `fcntl` at module level, so
# collection dies with ModuleNotFoundError before the first test — and 2025.10
# is our minimum, i.e. no supported HA version runs on Windows. Use WSL (or CI)
# for tests/integration; the pure core in tests/ stays fully cross-platform.
#
# TWO pinned HA targets (review plan E.11 / E.13):
#   requirements-test.txt        — HA-MIN: the promised minimum RELEASE SERIES
#                                  (README badge + hacs.json say 2025.10.0,
#                                  i.e. "2025.10.x and newer"); pytest-hacc
#                                  0.13.286 pins homeassistant==2025.10.1,
#                                  the newest patch of that series.
#   requirements-test-latest.txt — HA-LATEST: current stable, early warning
#                                  against API drift.
# Bump BOTH deliberately; a MIN bump must move the hacs.json minimum with it.
#
# E.13 (2026-08-15): MIN raised 2025.1.4 -> 2025.10.1. Reason: the two HA
# deprecations with a hard deadline — the hass-less
# `async_extract_config_entry_ids` (breaks in HA 2026.10) and the
# update-listener/reloading-flow-method combination (error from HA 2026.12) —
# can only be resolved WITHOUT compatibility shims from 2025.10 resp. 2025.3
# onwards. HA 2025.10 requires Python >= 3.13.2, hence the MIN CI job dropped
# 3.12. Deliberately NOT raised further: `UnitOfRatio` (2026.7) and
# `DeviceInfo["via_device_id"]` (2026.8) would push MIN onto the LATEST
# release itself, which would make the two-target matrix meaningless — and
# both are cosmetic (identical value, no runtime warning, removal not before
# 2027.8). See docs/reviews/2026-08-15-ha-drift-2026-02-bis-2026-08.md §5.1.
#
# WHY THE SERIES AND NOT THE EXACT .0 (asked in review, checked 2026-08-15):
# hacs.json promises 2025.10.0 while this pin tests 2025.10.1, so the claim is
# a series, not one build — the comments above say so instead of pretending
# otherwise. The exact floor WAS verified once: pytest-hacc 0.13.285 pins
# homeassistant==2025.10.0 and the full glue suite passes there (395 tests,
# same frontend wheel). It is deliberately not the permanent CI pin: HA
# 2025.10.0 depends on the PRE-RELEASE aiohasupervisor==0.3.3b0, which pip
# accepts (exact pin) but uv refuses without --prerelease=allow. That would
# split local verification from CI and leave a push-blocking gate hanging on a
# beta wheel staying on PyPI. Patch releases inside a series do not change the
# HA API surface, so the newest patch is the better permanent target.
#
# pytest-homeassistant-custom-component installs a *slim* Home Assistant that
# omits the (large) frontend wheel, but our manifest declares `frontend` as a
# dependency (it serves the Lovelace card), so HA refuses to set the
# integration up without `hass_frontend`. We therefore install it explicitly,
# pinned to the build HA 2025.10.1's frontend manifest declares.
pytest-homeassistant-custom-component==0.13.286
home-assistant-frontend==20251001.0

# aiodns 3.5.0 (pulled by this HA) calls `pycares.ares_query_a_result`, which
# pycares 5.x removed — an unpinned resolve installs 5.x and every HA import
# dies with AttributeError before a single test runs. HA's own constraints
# cap it; the slim harness does not, so pin it here.
pycares<5

# coverage plugin for the glue gate (pinned-compatible with pytest-hacc)
pytest-cov
